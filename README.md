# noctua-design

The Noctua design system: tokens and components, as **two packages that behave
identically** — a Dioxus crate and a React package — plus a documentation site.

## Before you clone

Clone this **only** inside `noctua-workspace/repos/`, and start your agents
**only** from the workspace root:

```sh
cd path/to/noctua-workspace   # the directory holding the .noctua-workspace marker
git clone <this repository> repos/noctua-design
claude                       # or whichever agent you use — from here, never from inside the repository
```

Anywhere else, this repository cannot reach the shared documents or its sibling
`noctua-colors`, whose output it vendors. An agent started inside it cannot read
either, and guesses instead of looking; it detects that itself and prints a loud
warning, so if you see one, close it and reopen it at the workspace root.

## Quick start

Requires only a Rust toolchain, and nothing to install first: the `cargo xtask`
alias ships in `.cargo/config.toml`, and the WebAssembly target is declared in
`rust-toolchain.toml`.

```sh
cargo xtask check     # validate spec/, run every gate, check the generated output
cargo xtask build     # compile spec/ into tokens, icons and dist/
cargo xtask dev       # ...and serve the docs site, rebuilding as sources change
```

`cargo xtask check` also runs formatting, lints and tests, and it is the same
command CI runs.

**Node is optional.** It is needed only for the React package and the browser
suite. The Rust half of this repository builds and tests without it, and
`cargo xtask check` proves that rather than assuming it.

## What is here

| Path | What it is |
|---|---|
| `spec/` | The source of truth: tokens, theme, icons, syntax, i18n, and one contract per component. **The only files you edit** to change any of them |
| `crates/noctua-design/` | The Dioxus package |
| `packages/react/` | The React package |
| `crates/noctua-design-tokens/`, `packages/tokens/` | **Generated** from `spec/`, and committed |
| `packages/tokens/vendor/` | The colour tokens, **generated by `noctua-colors`**. Never edited here |
| `assets/fonts/` | The subset fonts, their licences, and a reproducible attribution |
| `crates/noctua-design-styles/` | The component rules, hand-written. `sources()` is the order they load in |
| `dist/` | **Generated, committed**: the CSS layers, `components.css`, the behaviour modules and their manifests |
| `crates/noctua-design-dist/`, `packages/dist/` | **Generated**: `dist/` copied, because a registry cannot carry a file above a package |
| `crates/noctua-design-fonts/`, `crates/noctua-design-fonts-jp/`, `crates/noctua-design-fonts-kr/`, `crates/noctua-design-fonts-sc/`, `packages/fonts/` | **Generated**: the faces of `assets/fonts/` copied, for the same reason, and split because a registry refuses a crate over 10 MB |
| `examples/` | Two consumers from outside the workspace, and [what each proves](examples/README.md) |
| `docs-site/` | The documentation site, and [its own README](docs-site/README.md) |

Generated directories are committed so every consumer works with no build step.
`cargo xtask check` fails if one drifts from `spec/`.

## Use it in your own project

**There is no build step.** No Tailwind, no bundler, no preprocessor: the
stylesheets and the behaviour modules are generated and committed, and a page
links them.

### 1. A page, in three steps

```sh
npm i @noctua-world/design-dist
cp -r node_modules/@noctua-world/design-dist/dist static/dist
```

Then paste this file and open it. It is complete — nothing else is needed:

```html
<!doctype html>
<html>
  <head>
    <meta charset="utf-8" />
    <!-- Copy these <link>s from static/dist/base.html. The ORDER MATTERS. -->
    <link rel="stylesheet" href="static/dist/tokens/css/ramp.css" />
    <link rel="stylesheet" href="static/dist/scope.css" />
    <link rel="stylesheet" href="static/dist/tokens/css/theme-blue-balanced.css"
          id="noctua-base-palette" />
    <link rel="stylesheet" href="static/dist/tokens.css" />
    <link rel="stylesheet" href="static/dist/tones.css" />
    <link rel="stylesheet" href="static/dist/syntax.css" />
    <link rel="stylesheet" href="static/dist/fonts.css" />
    <link rel="stylesheet" href="static/dist/theme.css" />
    <link rel="stylesheet" href="static/dist/components.css" />
    <!-- Then paste the contents of static/dist/bootstrap.html here. -->
  </head>
  <body data-palette="blue-balanced" data-theme="dark">
    <button class="nd-button" type="button">
      <span class="nd-button-label">Save</span>
    </button>
  </body>
</html>
```

**One line adopts the typography.** No component sets a font — a design system
does not restyle the page it is installed into — so the faces the stylesheets
declare reach nothing until the page asks for them:

```css
body { font-family: var(--noctua-font-ui); }
```

**The two things that go wrong**, and they fail silently:

1. **The link order is load-bearing.** `base.html` is that list, generated —
   copy from it rather than retyping. `components.css` is last so your own
   stylesheet, linked after it, still wins.
2. **`bootstrap.html` has to run**, inline, in `<head>`. It stamps the theme
   attributes before the first paint. Without it — and without writing
   `data-palette` yourself, as above — the page has **no palette at all**.

### 2. Components, if you use React or Rust

```sh
npm i @noctua-world/design-react @noctua-world/design-dist
```

```jsx
import { Button } from "@noctua-world/design-react";

export default () => <Button label="Save" />;
```

```toml
# Cargo.toml
[dependencies]
noctua-design = "0.3.0"
dioxus = { version = "0.7", default-features = false, features = ["macro", "html", "signals", "hooks"] }

[build-dependencies]
noctua-design-dist = "0.3.0"
```

```rust
// build.rs — writes the files above into static/dist/
fn main() -> std::io::Result<()> {
    noctua_design_dist::write_to("static/dist")
}
```

```rust
use noctua_design::components::Button;
rsx! { Button { label: "Save" } }
```

`examples/consumer-rust/` and `examples/consumer-web/` are both of those,
working, from outside this workspace. Copy one and start there.

### 3. Behaviour, when a component needs a keyboard

A `Tabs` announces a role that obliges arrow keys; the module that carries them
is one import, and nothing pulls in the rest:

```html
<script type="module">
  import { enhanceTabs } from "./static/dist/tabs.js";
  enhanceTabs();
</script>
```

Each module exports `enhanceX(root)` and `releaseX(root)`. An app with a
client-side router calls the second one before it replaces markup.

### A drawer, and the window it stands in

A `Drawer` at the bottom of a window takes a share of the room the footer
leaves, and only a flex container can hand that out. Lay the window out as a
flex column with a height of its own, and let the work be the one other part
that grows, from nothing:

```css
.window { display: flex; flex-direction: column; block-size: 100vh; } /* allow-literal: an example of a consumer's own stylesheet */
.work   { flex: 1 1 0; min-block-size: 0; overflow: auto; }
```

In any other box with a height of its own the drawer takes its share of the
whole box, footer included. A work that starts from its content
(`flex: 1 1 auto`) can leave the drawer no room, and an open drawer then stands
at its floor, `--noctua-target-min`.

### With Tailwind

Nothing here needs Tailwind, and an application built on this system may use it.
`dist/tailwind/bridge.css` maps Tailwind v4's utilities onto the tokens: every
colour utility onto its `--nc-*` token, and the spacing scale, the radii, the type
sizes, line heights, weights, letter spacing and font roles, the shell's lengths,
the smallest target, the measure, the easings and the breakpoints onto their
`--noctua-*` tokens. It declares no colour and no length of its own. Link the sheets from
`base.html` as above, then import the bridge after Tailwind in the entry
stylesheet:

```css
@import "tailwindcss";
@import "./static/dist/tailwind/bridge.css";
```

`bg-surface`, `text-fg` and `border-border` then follow the palette, the mode and
a theme scope exactly as the components do, and `gap-4`, `p-inset`, `min-w-0`,
`h-shell-line`, `rounded-control`, `text-body`, `leading-body`, `font-semibold`
and `font-ui` are the design tokens by name.

**A step of the spacing scale is a name, and a number between two steps is no
utility.** The bridge declares `--spacing-4` and sets the bare `--spacing` to
`initial`, so `gap-4` is `var(--noctua-space-4)` and `gap-5` emits nothing,
under either import. That takes out Tailwind's multiplier and nothing else:
`@import "tailwindcss"` still brings Tailwind's own type sizes, radii and
palette (`text-sm`, `rounded-md`). Import `tailwindcss/utilities.css` in its
place where the tokens are meant to be the whole vocabulary.

**A duration, a layer and a border width are utilities by the token's name.**
Tailwind has no theme variable for them, and its own are bare numbers
(`duration-150`, `z-10`, `border-2`), which no token stands behind. The bridge
adds `duration-fast`, `z-dialog`, `border-hairline` with its sides
(`border-b-hairline`), `outline-focus` and `outline-offset-focus`, and maps
`ease-out`, `ease-in-out` and `ease-linear`. A `duration-fast` follows
`prefers-reduced-motion`, as the token does. The breakpoints are written as
lengths, and the scene tokens have no utility.

### The typefaces are packages of their own

`fonts.css` asks for every face at `../assets/fonts/<file>`: in `assets/fonts/`, <!-- allow-reference: a URL relative to wherever the consumer put the sheet, not a path in this repository -->
beside the directory you copied `dist/` to. The faces are 17 MB, more than a
registry lets one crate hold, so they are not in the package that carries the
sheets.

| Registry | Package | Faces |
|---|---|---|
| crates.io | `noctua-design-fonts` | the Latin faces, the code face, the symbols and eight other scripts, about 3 MB |
| crates.io | `noctua-design-fonts-jp`, `-kr`, `-sc` | one CJK family each, cut into slices |
| npm | `@noctua-world/design-fonts` | all of them, listed by set in `fonts.json` |

```rust
// build.rs
fn main() -> std::io::Result<()> {
    noctua_design_dist::write_to("static/dist")?;
    noctua_design_fonts::write_to("static/assets/fonts")
}
```

Every crate of faces writes flat into that one directory, by the names the
stylesheet uses, with the licence of each family beside it. A host that serves
from memory serves each entry of `FILES` at `assets/fonts/<name>` instead. A
face that is not served costs nothing but itself: the stacks fall back to the
system's fonts, and a face is fetched only when a page draws a character in its
range. The archive every release attaches carries `dist/`, the faces and their
licences together:
<https://github.com/noctua-world/noctua-design/releases/latest>.

### Working from a clone instead

Two directories become one static directory of yours — the same layout the
package produces:

| From | To | What it is |
|---|---|---|
| `dist/` | `<static>/dist/` | the stylesheets, the behaviour modules, the palettes and the theme data |
| `assets/fonts/` | `<static>/assets/fonts/` | the faces `fonts.css` asks for — copy the ones you use |

### A tagged commit instead of a release

Cargo can take the crate straight from a tag:

```toml
noctua-design = { git = "https://github.com/noctua-world/noctua-design", tag = "v0.3.0" }
```

A project inside the workspace, as `noctua-central` is, depends on
`path = "../noctua-design/crates/noctua-design"` instead, so the two can be
edited together, and keeps the tag form in a comment directly above it
(`NOCTUA.md §9.14`). Moving to the tag changes that one line, and the source of
`dist/` if the app copies it by hand: the checkout Cargo made, rather than the
sibling working tree.
